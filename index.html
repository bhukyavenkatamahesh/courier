Packet Game

A visual walkthrough of my networks project: building reliable, congestion-controlled file transfer on top of UDP — a protocol that offers neither — and then measuring whether two of my transfers share a bottleneck link fairly.

The problem

What UDP gives you

Fire a packet and hope. No ordering, no delivery guarantee, no notion of how fast the network can actually go. Packets vanish, arrive out of order, or arrive twice.

What a file transfer needs

Every byte, exactly once, in the right order — and a sending rate that adapts to the network instead of flooding it and starving everyone else on the link.

Everything in the gap between those two boxes is what I had to implement by hand. The simulation below is that implementation, running.

What's actually going on

Numbering every packet

Each packet carries the byte offset it starts at, so the receiver can put a jumbled stream back in order and spot a gap. In the code a packet is literally seq_num | data, with 1400 bytes of payload.

Why 1400? Ethernet's MTU is 1500 bytes. Staying under it means the network never has to fragment my packets — fragmentation would mean losing one fragment loses the whole packet.

Cumulative acknowledgements

The receiver doesn't ack each packet individually. It acks the next byte it still needs — "I have everything before this." One ack can therefore confirm many packets, and a lost ack is harmless because the next one supersedes it.

If a packet arrives early, the receiver buffers it and keeps asking for the missing one. Nothing is thrown away, and nothing is written to disk out of order.

The sliding window — how fast to send

The window is how many packets the sender is willing to have unacknowledged at once. Send one at a time and a 50 ms link wastes almost all its capacity waiting. Send everything at once and you drown the bottleneck.

So: start at 1, and double the window every successful round (slow start) until hitting a threshold, then grow by just one per round (congestion avoidance). Fast probing while it's safe, cautious probing once we're near the limit.

Detecting loss two different ways

Duplicate acks. If packet 5 is lost but 6, 7, 8 arrive, the receiver keeps repeating "I still need 5." Three of those and the sender resends immediately rather than waiting for a timer — this is fast retransmit. Data is still flowing, so the network isn't badly congested; the window is halved, not reset.

Timeout. Total silence means something worse. The sender resends and drops the window all the way back to 1.

Worth knowing: duplicate acks only exist if the receiver re-acks on every out-of-order arrival. My receiver buffers silently instead, so in the real code recovery almost always comes from the timer — the sender's fast-retransmit path is there but rarely reached. The simulation re-acks, so you can actually see it fire.

How long to wait before panicking

A fixed timeout is wrong everywhere: too short on a slow link and you flood it with needless resends, too long on a fast one and you stall. So the sender measures each round trip and keeps a running average plus a running measure of how much it varies:

timeout = estimatedRTT + 4 × deviation

The deviation term is what makes it adaptive — on a jittery link the sender automatically becomes more patient. Watch the patience number change as the simulation runs.

Why backing off is the whole point

Halving the rate on loss looks like it hurts the sender, and in isolation it does. But every sender on the link doing the same thing is what stops a shared bottleneck from collapsing — and it's what makes two transfers converge to roughly equal shares instead of one hogging the link.

That convergence is exactly what the second half of the project measures.

The experiment

The simulation above shows one transfer. The real question was what happens when two independent transfers share one bottleneck — and whether the congestion control I wrote divides that link fairly even when one client sits much further away.

Test bedMininet dumbbell topology, two client–server pairs, 100 Mbps bottleneck between the switches
VariableExtra delay on the second server's link, 0 → 100 ms in 20 ms steps, 5 runs each
Correctness checkMD5 of each received file compared against the original — the transfer is either byte-perfect or it failed
Fairness measureJain's index over the two throughputs: 1.0 is a perfectly equal split, 0.5 means one flow took everything
Why it's hardThe far client's feedback is slower, so it grows its window more slowly and is naturally at a disadvantage — fairness under asymmetric delay is the real test
